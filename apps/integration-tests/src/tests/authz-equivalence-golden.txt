# Authz equivalence golden baseline
# Snapshot of CURRENT resolver behavior — equivalence net, NOT a correctness oracle.
# Regenerate only after a reviewed, intentional change: UPDATE_AUTHZ_GOLDEN=1.
#
# Functions under snapshot:
#   private.authorize(perm)                        -> org boolean
#   private.app_authorize(perm, app)               -> per-app boolean
#   private.effective_app_permissions(app)         -> per-app permission set
#   private.get_org_permission_set(cr, role, tid)  -> org permission set
#
# App scopes (app_authorize / set columns), in order:
#   override_builtin : home-tenant app, per-app built-in role override = read
#   override_custom  : home-tenant app, per-app custom-role override (app.read, worker_run.insert, environment.promote)
#   org_fallback     : home-tenant app, NO per-app row → org-level fallback
#   other_tenant     : app in a DIFFERENT tenant → expected deny
#
# Org custom-role perms : app.read, dashboard.read, environment.read, trace.read, worker_run.read
# App custom-role perms : app.read, environment.promote, worker_run.insert
#
# Actors:
#   owner            role=owner member
#   admin            role=admin member
#   write            role=write member
#   read             role=read member
#   disabled         role=disabled member
#   org_custom       role=read org_custom_role member
#   app_scoped_read  role=read is_app_scoped member
#   platform_admin   role=none platform_admin NON_member
#   non_member       role=none NON_member
#
# DOWNWARD-OVERRIDE rows (silent-escalation review targets):
#   admin @ override_builtin — org-admin restricted to a built-in app-read override on one app
#   admin @ override_custom — org-admin restricted to an app-scoped custom-role subset on one app
#
# Baseline provenance: regenerated when app_authorize and the per-app permission
# set collapsed into ONE resolver (private.effective_app_permissions), structured
# as tenant-closure (I1) → state-gate (I2) → single resolution (I3). The only
# intended divergences from the pre-consolidation baseline, all within I1/I2/I3:
#   (a) other_tenant deny — an app outside the actor tenant is out of the resolver
#       domain (tenant closure), for every actor INCLUDING owner.
#   (b) disabled deny — a disabled membership yields no effective role, so a per-app
#       override has nothing to attach to (state gate).
#   (c) owner BOOL↔SET consistency — owner ignores per-app overrides (I3), so its
#       answers come from the org owner set, not from an override. environment.
#       promote is seeded to owner/admin/write in role_permissions, so those roles
#       hold it via the org role: it appears in the owner/admin/write org sets, in
#       owner's app sets at every in-tenant scope, and for admin/write at
#       org_fallback. read does not hold it. The app custom-role override already
#       carries environment.promote, so the override_custom answers are unchanged.
#
